# 1.3.0 测试端隔离约定

用户要求：必须单独开测试服务，不能替换正式端；新服务必须兼容旧客户端。

## 部署隔离

新增 `deploy/compose.preview.yaml`，不修改正式 `deploy/compose.yaml`：

- 独立项目名 `autoscript-hub-preview` 和服务名 `preview_server`。
- 只使用独立命名卷 `preview_data`，不绑定正式目录或数据库。
- 测试镜像、端口、JWT 密钥和管理员密码必须显式填写，不继承正式配置。
- 默认绑定 `127.0.0.1`；对外入口或反向代理另行确认。
- 默认限制 512 MiB 内存、1 CPU，避免测试服务无界挤占正式服务资源；这是容器限制，不代表客户端脚本有同样配额。
- 测试端默认关闭企业外部认证，使用独立合成账号。

仅在确认独立部署目录和测试入口后，才把公开模板复制到该目录，在其 `deploy/.env` 中填写私有值。不得覆盖正式 `deploy/.env`，不得把两个 Compose 文件合并使用，不执行 `--remove-orphans`，不启动现有正式升级脚本。检查配置时使用 `docker compose --env-file .env -f compose.preview.yaml config --quiet`，避免把密钥输出到日志。

当前只有本地隔离验收与部署模板，尚未在公司服务器启动该测试实例。

## 旧客户端兼容策略

- 使用冻结 `v1.2.4` 的原始客户端代码，而非用新客户端模拟旧请求。
- 登录、注册、心跳、旧 pending/claim、脚本下载、状态和日志接口保留；WS 不是旧客户端的前置要求。
- 旧客户端一次上传全部未确认日志，不能给该旧端点新增 1 MiB 限额。只对此端点保留原载荷行为，并把认证、运行归属和受管记录拒绝放在读取正文之前。新任务/诊断的数据限制不变。反向代理和容器容量仍需按实际日志规模设置，未承诺无限日志容量。
- 旧 pending 查询显式排除受管执行和已导入历史，避免旧客户端 `limit=1` 被异常历史状态阻塞。
- 旧工单三字段请求仍可报单，但没有显式同意时不自动附加诊断。旧界面的“自动附带”文案不会因此变真；这是必须向用户说明的隐私兼容边界。
- 新工单长度/格式限制仍有效；校验失败返回安全字符串，避免旧 UI 渲染 Pydantic 错误对象崩溃，也不回显敏感输入。

实际测试结果见后续验收记录；模板检查不能替代远程部署验收、实际旧安装包及双设备业务验证。
