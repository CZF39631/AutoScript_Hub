# AutoScript Hub 0.9 局域网部署与运维

本文适用于 `linux/arm64`（aarch64）与 `linux/amd64`（x86-64）单机部署。0.9 使用 SQLite，只允许一个服务端副本。

## 首次部署

```bash
unzip autoscript-hub-server-deploy-0.9.0.zip
cd autoscript-hub-server
cp deploy/.env.example deploy/.env
id -u
id -g
```

编辑 `deploy/.env`：

- 把 `JWT_SECRET` 与 `ADMIN_PASSWORD` 替换为真实随机值。
- `AUTOSCRIPT_DATA_DIR` 使用主机绝对路径，例如 `/opt/autoscript-hub/data`。
- `AUTOSCRIPT_UID`、`AUTOSCRIPT_GID` 填入运行目录所有者的 UID/GID。
- 默认绑定 `0.0.0.0`，因此局域网设备可以访问；不要直接暴露到公网。

```bash
sudo install -d -o "$(id -u)" -g "$(id -g)" /opt/autoscript-hub/data
docker compose --env-file deploy/.env -f deploy/compose.yaml up -d
docker compose --env-file deploy/.env -f deploy/compose.yaml ps
curl --fail http://127.0.0.1:8000/api/health/ready
```

局域网地址为 `http://服务器IP:AUTOSCRIPT_PORT`。就绪响应中的 `database`、`data_dir`、`migration` 应全部为 `ok`。

## 国内网络和镜像代理

下面的源码构建命令只适用于完整源码仓库；独立部署 ZIP 使用已经发布的 GHCR 镜像，不包含应用源码。完整源码仓库默认使用 Docker Hub。若 Docker Hub 不可达，可在 `deploy/.env` 设置兼容代理，不必修改 Docker daemon：

```dotenv
AUTOSCRIPT_BASE_REGISTRY=docker.m.daocloud.io/library
```

然后构建：

```bash
docker compose --env-file deploy/.env \
  -f deploy/compose.yaml -f deploy/compose.local.yaml up -d --build
```

若 `docker info` 显示不可达的 HTTP/HTTPS Proxy，应先恢复该代理，或由主机管理员修改 Docker 服务代理并评估重启对现有容器的影响。

## 日常检查和日志

```bash
curl --fail http://127.0.0.1:8000/api/health
curl --fail http://127.0.0.1:8000/api/health/ready
docker compose --env-file deploy/.env -f deploy/compose.yaml ps
docker compose --env-file deploy/.env -f deploy/compose.yaml logs --tail=200 server
docker compose --env-file deploy/.env -f deploy/compose.yaml logs -f server
```

上面的完整命令等价于在已设置默认 Compose 文件时使用 `docker compose logs server`；运维时应保留 `--env-file` 和 `-f` 参数以避免读错项目。

容器日志写入 stdout/stderr；数据库、脚本、业务日志、备份和临时文件均位于 `AUTOSCRIPT_DATA_DIR` 映射的 `/data`。

## 在线备份

备份通过容器内 Python 和 SQLite 在线备份 API 执行，主机不需要额外安装 Python 包：

```bash
AUTOSCRIPT_DATA_DIR=/opt/autoscript-hub/data sh ops/server/backup.sh
```

同一主机运行多套 Compose 时，为所有运维命令增加与启动时一致的 `AUTOSCRIPT_PROJECT_NAME`。

命令返回 `/data/backups/<时间>-<版本>`。目录包含数据库副本、脚本、清单和 SHA-256。真实 `deploy/.env` 不包含在数据备份中，应另行保存。

## 停止恢复

恢复会覆盖当前数据，必须先停止服务，并指定 `/data/backups/...` 或对应的主机绝对路径：

```bash
docker compose --env-file deploy/.env -f deploy/compose.yaml stop server
AUTOSCRIPT_DATA_DIR=/opt/autoscript-hub/data \
  sh ops/server/restore.sh /data/backups/<时间>-<版本>
docker compose --env-file deploy/.env -f deploy/compose.yaml up -d server
curl --fail http://127.0.0.1:8000/api/health/ready
```

`restore.sh` 会先验证清单、大小和 SHA-256，校验失败不会恢复。

## 升级

升级脚本先备份，再拉取目标镜像、重建容器并检查就绪；失败会调用回滚：

```bash
AUTOSCRIPT_DATA_DIR=/opt/autoscript-hub/data \
  AUTOSCRIPT_SERVER_IMAGE=ghcr.io/czf39631/autoscript-hub-server:0.9.0 \
  sh ops/server/upgrade.sh 0.9.1
```

升级成功后，把 `deploy/.env` 中的 `AUTOSCRIPT_SERVER_IMAGE` 固化为完整 SemVer 镜像引用，防止下次手工 Compose 启动回到旧标签。升级失败时脚本会记录并使用升级前容器的不可变镜像 ID 执行恢复。

完全离线的局域网主机可以由管理员先用 `docker load` 导入目标镜像，然后显式设置 `AUTOSCRIPT_SKIP_PULL=1`：

```bash
AUTOSCRIPT_DATA_DIR=/opt/autoscript-hub/data \
  AUTOSCRIPT_SERVER_IMAGE=ghcr.io/czf39631/autoscript-hub-server:0.9.0 \
  AUTOSCRIPT_SKIP_PULL=1 \
  sh ops/server/upgrade.sh 0.9.1
```

该开关只跳过远端拉取；脚本仍会备份、重建、迁移和检查就绪。默认不设置时始终拉取发布镜像。

## 从维护电脑一键远程升级（推荐）

仓库提供 `ops/server/remote_upgrade.py`，用于把“连接检查 → 上传当前运维脚本 → 在线备份 → 拉取正式镜像 → 重建和迁移 → 连续健康检查 → 固化镜像版本”串成一次操作。升级失败时仍由 `upgrade.sh` 自动恢复升级前数据库和不可变镜像，远程脚本同时恢复原 `.env`。

首次在维护电脑配置：

```bash
cp ops/server/remote-upgrade.env.example ops/server/remote-upgrade.env
```

编辑 `remote-upgrade.env`，填写 SSH 主机、用户、私钥、远程 Compose 文件、数据目录、项目名和端口。该文件已被 Git 忽略，不得提交真实内网地址；JWT、管理员密码、外部认证地址等应用密钥仍只保存在远程服务器的 `.env`，不要复制到本机配置。

日常发布镜像已完成后，只需修改 `TARGET_VERSION` 并直接运行：

```bash
python ops/server/remote_upgrade.py
```

临时覆盖目标版本时可使用：

```bash
python ops/server/remote_upgrade.py --version 1.2.0
```

脚本遵循以下固定顺序：

1. 本机校验配置、SemVer、SSH 私钥和 `ssh`/`scp` 命令。
2. 上传经过 SHA-256 校验的当前 `ops/server` 工具包；不上传本机密钥或服务端配置。
3. 远程确认 Docker、Compose 文件、数据目录和升级前健康状态。
4. 在远程部署目录的 `history/` 备份 `.env`，并把镜像固定为完整 SemVer。
5. 调用 `upgrade.sh` 在线备份 SQLite、拉取镜像、重建服务并执行迁移。
6. 要求健康响应中的版本与目标版本完全一致，且数据库、数据目录和迁移检查均为 `ok`。
7. 无论成功或失败都删除 `/tmp` 中的临时运维工具包；业务备份和 `.env` 历史备份保留。

注意：正式环境默认 `SKIP_PULL=0`，确保使用发布仓库中的镜像。只有已通过 `docker load` 导入目标镜像且确认标签正确时，才临时设置 `SKIP_PULL=1`。

## 服务端自动缓存客户端更新

服务端可在启动后立即检查 GitHub Release，并按设定周期下载、验签和缓存 Stable/Beta Windows 安装包。客户端从当前服务器读取缓存失败时，仍会回退到公开更新源。

管理员通过 API 配置，客户端每用户的 `proxy` 设置不会影响服务端：

```bash
curl -X PUT http://127.0.0.1:8000/api/settings/server-update \
  -H "Authorization: Bearer <管理员登录令牌>" \
  -H "Content-Type: application/json" \
  -d '{
    "enabled": true,
    "outbound_proxy": null,
    "github_repository": "CZF39631/AutoScript_Hub",
    "interval_hours": 6
  }'
```

配置代理时，`outbound_proxy` 可使用 `http://代理地址:端口` 或 `https://代理地址:端口`；保存后会立即唤醒检查任务。代理凭据仅存储在服务端数据库中，不写入审计详情或日志。读取当前配置：

```bash
curl http://127.0.0.1:8000/api/settings/server-update \
  -H "Authorization: Bearer <管理员登录令牌>"
```

服务端只接受已签名清单中指向所配置 GitHub 仓库的完整 EXE，下载时忽略历史 Gitee 分卷，并在大小和 SHA-256 校验完成后原子发布。默认关闭自动缓存，需由管理员显式启用。

## 人工回滚

必须同时指定旧镜像版本和与它匹配的升级前备份：

```bash
AUTOSCRIPT_DATA_DIR=/opt/autoscript-hub/data \
  sh ops/server/rollback.sh 0.9.0 /data/backups/<升级前备份>
```

回滚完成后再次检查 `/api/health/ready`、登录、脚本列表和日志。

## 持久化验收

1. 登录并上传一个测试脚本，执行一次并产生日志。
2. 执行 `docker compose ... down`，不得删除 `AUTOSCRIPT_DATA_DIR`。
3. 再次 `docker compose ... up -d`。
4. 确认账号、脚本、运行记录和日志仍存在。
5. 做一次备份、产生新数据、停止服务、恢复备份，确认新数据消失而备份时的数据存在。

## 局域网发布缓存（可选）

局域网发布缓存让客户端从局域网服务端下载更新清单和安装包，无需访问外网。服务端在 `/data/release-cache` 下存储最近 3 个版本的清单、签名和安装包，匿名提供读取。

### 服务端配置

编辑 `deploy/.env`：

```dotenv
# 设置同步令牌后，自托管 Runner 才能上传新版本到服务端。
# 留空则禁用上传端点（匿名读取仍可用）。
RELEASE_CACHE_SYNC_TOKEN=请替换为长随机值
```

服务端自动使用镜像内置的 Ed25519 公钥验证上传清单签名。无需在服务端配置私钥。

### GitHub Actions 自托管 Runner

局域网内的 Linux 主机上安装 GitHub Actions self-hosted runner（不要注册到公网服务器）。在 GitHub 仓库 Settings → Actions → Runners 注册后，记录自定义标签（例如 `lan`）。

在 GitHub 仓库配置：

- **Variables**（Settings → Secrets and variables → Actions → Variables）：
  - `LAN_INSTALLER_URL_BASE`：局域网服务端的外部地址，例如 `http://192.168.1.10:8000`。此值会写入签名后的 LAN 清单，必须与客户端实际访问地址一致。
  - `LAN_RUNNER_LABEL`：自托管 Runner 的自定义标签，例如 `lan`。
- **Secrets**（Settings → Secrets and variables → Actions → Secrets）：
  - `LAN_SYNC_TOKEN`：与 `deploy/.env` 中 `RELEASE_CACHE_SYNC_TOKEN` 相同的值。

配置完成后，每次推送 `v0.9.*` 或 `v1.*` 标签时，GitHub 托管的 `publish` 作业会：

1. 用 `UPDATE_PRIVATE_KEY_B64` 签名公开清单和 LAN 清单（私钥从不离开 GitHub 托管环境）。
2. 将 LAN 清单、签名和安装包打包为私有 workflow artifact（不公开到 Release）。

随后条件触发的 `lan-sync` 作业在局域网自托管 Runner 上运行，**仅使用 `LAN_SYNC_TOKEN`**，下载 artifact 并上传到服务端 `/api/release/sync`。

### 验证缓存

```bash
curl http://127.0.0.1:8000/api/release/versions
curl http://127.0.0.1:8000/api/release/manifest
curl http://127.0.0.1:8000/api/release/manifest.sig
```

### 客户端配置

在客户端「设置 → 客户端更新」中，将 LAN 清单地址放在首行（列表顺序即优先级）：

```
http://<服务端IP>:<端口>/api/release/manifest
```

客户端仍会验签清单、校验安装包长度和 SHA-256，验证逻辑与公开源完全一致。LAN 清单中的安装包 URL 指向同一服务端，因此下载不经过外网。
